# Анализ логов на DAMP: разбор идеи, реализации и базовый вариант

Документ отвечает на три вопроса: годится ли подход статьи
[«Discrete approach to machine learning»](https://arxiv.org/abs/2508.00869) ([текст](DAMP_extracted.txt))
для поиска инсайтов в логах, что из реализации в этом репозитории для этого пригодно, и как устроен
базовый вариант ([log_insights.py](../log_insights.py),
[damp/encoding/log_encoder.py](../damp/encoding/log_encoder.py)). Номера в скобках — параграфы статьи.

## 1. Вывод

- Идея рабочая. Строка лога укладывается в схему морфологии из §7.1 почти без натяжек: строка — «слово»,
  слова строки — «символы», повторяющиеся куски строк — «морфемы». Путь «стимул → раскладка → детекторы →
  эмбеддинг» (рис. 23) проходит целиком на общих `Layout` и `ActivationEngine`.
- Формат лога знать не нужно. Правил под формат в конвейере нет: заголовок строки и переменные места
  находятся по статистике. Проверено на логах DAMP и на пяти публичных логах других форматов (раздел 6).
- На логах самого DAMP базовый вариант нашёл упавший запуск, точное место сбоя и то, что ему
  предшествовало; разделил события на семейства и типы; выдал правила следования событий.
- Сильная сторона подхода — не подсчёт шаблонов, а единое пространство сходства: новая строка оценивается
  по частям, строка, окно и запуск кодируются одним механизмом, похожие инциденты ищутся нечётким поиском.
- Главные ограничения: эмбеддинги структурные, а не смысловые (§7, §10.1.3); метод рассчитан на сотни тысяч
  точек, а в логах различных строк мало; порядок событий внутри окна теряется; тип события на практике
  определяется первичным кодом строки, раскладка и детекторы к нему мало добавляют (раздел 7).

Опоры в статье нет у двух шагов предобработки — отбрасывания фоновых слов и выделения переменных мест
(`BackgroundWords`, `VariableSlots`). Они помечены в коде как «вне статьи»; зачем они нужны, сказано в разделе 5.

Отдельно полезна §7.2 (гистохимические маркеры): там точка — вектор совместной выраженности маркеров
в окне, и раскладка показывает, какие маркеры встречаются вместе. Для логов это раскладка второго уровня:
окна строк как «цилиндры» по времени. В базовый вариант она не вошла (раздел 8).

## 3. Чего статья для логов не даёт

1. **Смысл.** Эмбеддинги отражают строение строки (§7: «structural and not semantic»). `connection refused`
   и `cannot connect` близки, только если у них есть общие слова.
2. **Время.** Набор стимулов S (§6.5) — множество: порядок строк в окне теряется. Список из §2.3.2 хранит
   пары соседей, но не длительности и не периодичность.
3. **Малые данные.** Пространства статьи — от 0.4 до 3 млн точек (§7.1.8); кластеры и детекторы там
   опираются на сотни точек. В логах различных строк обычно сотни или тысячи.
4. **Редкие события.** Точка без похожих соседей имеет нулевую энергию и в детекции не участвует
   (§6.3, §6.5: «тот же способ отсекает выбросы») — это свойство метода. Единичная уникальная строка
   эмбеддинга не получает; её ловит только проверка новизны.
5. **Константа или переменная.** В морфологии любое различие слов значимо. В логах часть слов — значения
   (имя пользователя, хост), и статья их от остальных не отличает.
6. **Готовые значения параметров.** Пороги и бюджеты бит статья подбирала по ходу дела и шесть раз
   меняла коды морфологии (§7.1.8.1–§7.1.8.6). Для логов их тоже пришлось измерять.

## 4. Реализация в репозитории: что общее, а что про MNIST

Реализация делится на алгоритм статьи и на конвейер MNIST вокруг него.

| Компонент | Для логов | Комментарий |
|---|---|---|
| `BitArray`, `LayoutCodeTable` | переиспользованы | общие |
| `Encoder`, `Dimension`, `geometric_detector_layers` | переиспользованы для чисел | широкие детекторы кодируют непрерывные величины; текст они не кодируют, поэтому для слов добавлен `TokenAlphabet` |
| `Layout` (обе фазы, расписание §7.1.7, энергии §5.7, карты §5.14) | переиспользован как есть | режим статьи: `φ = Σ s·d`, жёсткий порог |
| `DbscanClusterer`, `DetectorHierarchyBuilder`, `DetectorOutputSizer` | переиспользованы как есть | не зависят от вида стимулов |
| `ActivationEngine` | переиспользован: по экземпляру на слой детекторов и один для сборки кода | см. находку 1 |
| `LOGGER` | переиспользован | все события — внутри реализаций, с номером параграфа |
| `LayoutParameterTuner`, `_sparse_layout_options` из `main.py` | переиспользованы | дают число пар и шагов; расписание λ и радиуса задано своими константами `LOG_LAYOUT_*` |
| `MnistSobelAngleMap`, `angle_position_sketch`, `damp/decode` | не нужны | извлечение стимулов из картинок и k-NN по классам цифр |
| Иерархия «части → композиция» и чекпоинты в `main.py` | не нужны | специфика MNIST |
| `SeededPlacement`, шаг на устройстве, ядра CUDA, сглаживание (`LAYOUT_SMOOTH_PINWHEELS`) | не нужны | раскладки от 10⁵ точек и расширение статьи для пинвилов |
| `LAYOUT_EMPTY_RATIO = 0.5`, слои детекторов 0.7–0.9, `component_period` | не взяты | подобраны под MNIST; для логов — значения статьи |

Находки по реализации, сделанные при переносе на логи:

1. **Один порог активации на все слои.** `ActivationEngine` активирует пространство с одним `λ_a`
   (у MNIST он равен порогу нижнего слоя). Энергия детектора `e_d` считается с порогом своего слоя `λ_d`
   (§6.3), поэтому у слоёв с `λ_d > λ_a` уровень `E(d, A) = Σ a·e / e_d` не ограничен: на логах он доходил
   до 11.2, а строка активировала в среднем 129 детекторов из 874. §7.1.10 говорит: «каждое значение λ_a
   задаёт свой слой иерархии детекторов». `LayeredDetection` оценивает каждый слой по активации с порогом
   этого слоя: активных детекторов на строку стало около 20.
2. **Случайный выходной бит с повторами.** `DetectorHierarchyBuilder` и `reassign_output_bits` выдают
   детектору случайный бит независимо от остальных. В первом прогоне 874 детектора приходились на 248
   различных бит из 256, и у строк с коротким кодом возникало ложное сходство. Для логов биты выдаются
   перестановкой без повторов (как кодер выдаёт биты детекторам слоя), длина кода — не меньше числа
   детекторов. Паразитное сходство непохожих строк упало с 0.086 до 0.036.
3. **Энергия точки считается с текущим λ раскладки.** После расписания §7.1.7 это 0.8. Детекторам
   нижних слоёв нужна энергия с их порогом, поэтому перед расчётом вызывается
   `set_similarity_params(lambda_threshold=LOG_ENERGY_LAMBDA)`.
4. **Константы и настройка живут в `main.py` рядом с MNIST.** `LayoutParameterTuner` зависит от флага
   `LAYOUT_SMOOTH_PINWHEELS`; `LAYOUT_EMPTY_RATIO` равен 0.5 при 15 % в статье (тест
   `test_default_empty_ratio_matches_space_filling_margin` на `main` из-за этого не проходит). Логи от этих
   значений не зависят: у них свои `LOG_*`.
5. **Rerun.** В каждом запуске в лог попадает `RerunWarning … ArrowTypeError`: поле события меняет тип
   между записями. Анализ логов сам пометил эти строки как проблемные и присутствующие во всех запусках.
   Для пакетных прогонов надёжнее `RERUN=off`.
6. **Пул процессов.** `Layout` строит таблицу сходства в пуле процессов; на Windows скрипту нужен
   `if __name__ == "__main__":`. Именно такой сбой разобран в разделе 6.
7. **Без torch всё идёт на CPU**, и на этом размере этого хватает: полный прогон — около 80 секунд.

## 5. Базовый вариант

Логи делятся на **эталонные** (по ним строится пространство) и **целевые** (в них ищутся новизна и
инциденты). Целевой файл может входить и в эталон. Каждый файл — один запуск.

1. **Строка → токены → слова** (§7.1.3). Метки времени распространённых видов (ISO, syslog, asctime, журнал
   веб-сервера, просто время) убираются. Строка делится на токены по пробелам, знакам равенства, запятым,
   скобкам и кавычкам; токен — на слова по небуквенным символам и по заглавным буквам внутри слитных имён.
   Буквы — любого алфавита, длина слова 2–20 символов, строка — до 32 слов. Токен без слов (число,
   идентификатор, адрес) — значение: в строке на его месте остаётся заполнитель `*`. Число записывается
   со слотом — двумя словами перед ним; числа подряд получают слот с порядковым номером.
2. **Фоновые слова** (вне статьи). Слово, стоящее не меньше чем в 90 % строк эталона, — это заголовок
   (хост, процесс, уровень); в код оно не входит. Иначе все строки получают общие биты, и порог λ
   перестаёт разделять кластеры — то же паразитное сходство, из-за которого статья меняла коды (§7.1.8.3).
3. **Переменные места** (вне статьи). Единица строки заменяется заполнителем, если при том же окружении
   на её месте встречается не меньше трёх разных единиц или в какой-то строке там стоит значение:
   `invalid user admin from` и `invalid user guest from` становятся `invalid user * from`. Окружение —
   не меньше двух единиц со словами, поэтому `session opened` и `session closed` остаются разными.
4. **Словарь фрагментов** (§7.1.3). Все подряд идущие группы до 8 слов; вес — сумма по строкам, где фрагмент
   встречается, доли его длины в длине строки.
5. **Разбиения** (§7.1.4). Для каждого числа фрагментов от 1 до 5 — разбиение наибольшего суммарного веса.
6. **Код разбиения** (§7.1.4.1, §7.1.4.4, §7.1.4.5). 256 бит. Слово на позиции внутри фрагмента — 40 цветных
   бит, в код идут первые по приоритету. Бюджеты фрагментов — табл. 3 статьи. Каждое разбиение кодируется
   с акцентом на начало и на конец строки: до 9 точек на строку. Заполнители в код не входят.
7. **Раскладка** (§7.1.6, §7.1.7). Запас пустых ячеек 15 %, cosine, λ от 0.65 до 0.8 шагом 0.05 с жёстким
   порогом, радиус пар от d/2 к 1; смена этапа — когда обмены падают до 1 % от начала этапа.
8. **Детекторы** (§6.4, §7.1.10, табл. 5). Шесть слоёв: λ_d = 0.5, 0.6, 0.7, 0.75, 0.8, 0.85.
9. **Эмбеддинг** (§6.5, §6.6, §7.1.12). Строка активирует пространство всеми своими кодами; код —
   colour merge бит активных детекторов; длина и насыщенность — по среднему числу активных детекторов.
   Код окна и запуска — та же детекция набора строк.
10. **Два кода для группировки.** Код типа — отклик пространства на код строки целиком (в нём каждое слово
    весит поровну), детекторы слоёв от 0.75. Код семейства — отклик на коды с акцентом на начало строки
    (§7.1.4.5), детекторы слоёв до 0.6. Тип отвечает на вопрос «что за событие», семейство — «чьё оно».
11. **Инсайты**: типы и семейства, новизна строк и чисел, инциденты с похожими окнами эталона, правила
    следования событий.

Параметры кодирования выбраны по измерению сходства кодов до раскладки (§5.13.4: дело в кодах, а не
в раскладке). На логах DAMP у случайных пар кодов сходство в среднем 0.14 (90-й процентиль 0.25), у строк
разных подсистем 90-й процентиль 0.22, у разных строк одного события медиана 0.36 и 90-й процентиль 0.78;
плотность кода не выше 20 % при пределе 25 % (§2).

### Отступления от статьи

| Что | В статье | Здесь | Почему |
|---|---|---|---|
| Группа букв и цифр с цифрой | цифры — разделители | словом не считается | обрывки идентификаторов и хешей давали случайные слова |
| Заголовок строки | нет | слова из ≥ 90 % строк не кодируются | общие биты у всех строк стирали различия между событиями |
| Переменные слова | различаются сходством кодов | заменяются заполнителем по статистике | в короткой строке переменное слово меняет код сильнее, чем различие двух событий в длинной |
| Учёт строк в словаре | частоты по корпусу | каждая различная строка один раз | строка, повторённая 2000 раз, подавляла остальные |
| Отбор разбиений | вес выше медианы среди всех разбиений | лучшее по весу на каждое число фрагментов | сумма весов всегда растёт с числом фрагментов: медиана оставила бы только самые мелкие |
| Бюджет внутри фрагмента | «равномерное смешивание» | по кругу, не меньше бита на слово | длинный фрагмент работает как хеш (§7.1.4.4) |
| Детекция | один `λ_a` (§6.5) | слой оценивается с порогом своего слоя | прочтение §7.1.10; находка 1 |
| Выходной бит детектора | случайный (§6.3) | случайный без повторов | находка 2 |
| Тип события | нет | отклик на код строки целиком | тип по всем кодам строки склеивал события одного компонента с разными сообщениями |
| Семейства, правила с поддержкой и подъёмом, список проблемных слов | нет | добавлены | прикладной слой поверх кодов |

## 6. Результаты

### Логи DAMP

Эталон: `layout.log`, `evaluate.log` и три удачных прогона пинвил-теста из `log_samples/`. Цель:
`log_samples/baseline_run.log` — прогон, упавший при запуске пула процессов. Отчёт:
[log_insights.md](../log_insights.md).

| Величина | Значение |
|---|---|
| Строк со словами / различных строк | 6879 / 234 (170 в эталоне, 64 только в цели) |
| Точек пространства, сетка | 1541, 43×43 |
| Раскладка | 3144 шага дальней фазы (λ дошёл до 0.8), 40 шагов ближней |
| Детекторов по слоям 0.5 … 0.85 | 42, 64, 105, 165, 128, 286 — всего 790 |
| Активных детекторов на строку | 20 |
| Код строки / окна | 1024 бита, до 20 / до 95 единиц |
| Время полного прогона на CPU | около 80 с |

- **Эмбеддинг наследует сходство первичных кодов** (§6.2): корреляция 0.77; у похожих строк сходство
  эмбеддингов в среднем 0.33, у остальных 0.028.
- **Семейства.** 119, из них 19 объединяют несколько видов строк. Крупнейшее — `layout`: 77 видов строк,
  70 типов, 5448 строк; дальше `encoder`, `decoder`, `hierarchy`, события сохранения файлов.
- **Типы.** 219. Ни один тип не объединяет события с разными именами. У 14 из 117 имён строки разошлись
  по нескольким типам (например, `layout.visual` с разным набором ключей).
- **Новизна.** Из 115 различных строк упавшего прогона 51 известна точно, 7 — по частям, 57 неизвестны.
  Все 64 новые строки — текст трассировки и её последствия; ни одна обычная строка в новые не попала.
- **Инцидент.** Один: строки 321–432, первый сигнал — строка 348 (`Traceback`). Перед ним:
  `layout.sim_cache.parallel workers=14` — сбой произошёл при запуске пула процессов, что и было причиной.
  Похожие окна удачных прогонов найдены со сходством 0.82, 0.74 и 0.74: до сбоя прогон шёл как обычно.
- **Сходство запусков.** Удачные прогоны пинвил-теста близки друг к другу (0.80–0.93), упавший отстоит
  от них (0.47–0.55), логи MNIST далеки от всех (не выше 0.18).
- **Связи.** 99 правил; самые сильные — цикл раскладки: после `layout.run.progress` в 99 % случаев идёт
  `layout.energy.long.progress` (поддержка 300).
- **Числа.** Новых значений нет: упавший прогон шёл с теми же настройками. Сам механизм проверен тестами.

Результат воспроизводим: два прогона с разными хеш-зёрнами Python дают побайтно одинаковые отчёт,
JSON и карты.

### Логи других форматов

Проверка на пяти публичных логах из набора [loghub](https://github.com/logpai/loghub) (по 2000 строк,
с разметкой шаблонов) и на шести файлах логов DAMP, где шаблон — имя события. Разметка в конвейер
не передаётся. Число — доля строк, сгруппированных в типы точно так же, как в разметке.

| Лог | Формат строки | Первый вариант | Сейчас |
|---|---|---|---|
| Apache | `[Sun Dec 04 04:47:44 2005] [notice] …` | 0.72 | 1.00 |
| HDFS | `081109 203615 148 INFO dfs.DataNode$…: …` | 0.33 | 1.00 |
| Zookeeper | `2015-07-29 17:41:44,747 - INFO [поток:класс@строка] - …` | 0.27 | 0.96 |
| DAMP | `имя.события ключ=значение … [§]` | 0.51 | 0.92 |
| Linux | `Jun 14 15:16:01 combo sshd(pam_unix)[19939]: …` | 0.00 | 0.69 |
| OpenSSH | `Dec 10 06:55:46 LabSZ sshd[24200]: …` | 0.23 | 0.49 |

Что дало прирост: метки времени и заголовок перестали попадать в код; переменные слова заменяются
заполнителем; тип определяется по коду строки целиком. Слой детекторов, с которого берётся код типа
(0.75, 0.8 или 0.85), на эти числа не влияет.

Остаточные расхождения — вопрос зернистости, а не формата:

- **OpenSSH.** В один тип попадают шаблоны, отличающиеся одним словом в длинной строке:
  `authentication failure … rhost=*` с полем `user` и без него, `failed password` и `failed none`.
  По чистоте типов дела лучше: в типах без примеси чужих шаблонов 68 % строк.
- **Linux.** Разметка различает шаблоны по конкретному имени пользователя, а у нас имя — переменная.
  Строки ядра вида `Dentry cache hash table entries`, `Inode-cache hash table entries` слились в один тип:
  первое слово встретилось в трёх вариантах и было принято за переменную.

Новизна проверена отдельно: пространство строилось по первым трём четвертям лога, целью была последняя
четверть (500 строк).

| Лог | Строк с известным шаблоном: всего / ложно помечено новыми | Строк с новым шаблоном: всего / помечено |
|---|---|---|
| HDFS | 499 / 0 | 1 / 1 |
| Zookeeper | 497 / 1 | 3 / 3 |
| OpenSSH | 499 / 0 | 1 / 1 |
| Linux | 384 / 0 | 116 / 116 |

Полный конвейер на трёх из этих логов (Zookeeper, Linux, OpenSSH) отрабатывает и даёт читаемые правила:
в OpenSSH — `authentication failure` → `failed password for * from * port` → `received disconnect … bye bye`,
в Linux — `session opened for user` → `session closed for user` с уверенностью 1.0. Качество инцидентов
и правил на чужих логах оценено только на глаз: разметки для них нет.

Тесты: [tests/test_log_insights.py](../tests/test_log_insights.py) и
[tests/test_log_formats.py](../tests/test_log_formats.py) — 35 тестов. Среди них сквозной прогон
на синтетическом логе с подложенной чужой строкой и числом вне диапазона и проверка, что одни и те же
12 событий в пяти оформлениях строки (простой текст, syslog, asctime, ISO, JSON) дают ровно 12 типов.

## 7. Ограничения базового варианта

- **Тип события — это почти первичный код.** Прямое сравнение кодов целых строк без раскладки и детекторов
  группирует строки в типы не хуже. Раскладка и детекторы нужны для семейств, кодов окон и оценки новой
  строки по частям; для одной только группировки в шаблоны они избыточны.
- **Одно слово в длинной строке.** Строки из десятка слов, отличающиеся одним словом, попадают в один тип.
  Для `failed none` и `failed password` это ошибка.
- **Переменная или три разных события.** Слово, встретившееся в одном окружении в трёх вариантах, считается
  переменной. `connection opened to db`, `connection closed to db`, `connection lost to db` сольются.
- **Метки времени.** Распознаются перечисленные виды с английскими названиями месяцев. Месяц на другом
  языке станет словом; если он стоит в каждой строке, его уберёт правило фоновых слов, иначе он попадёт в код.
- **Фоновые слова** ищутся в эталоне не меньше чем из 50 строк.
- **Корпус мал.** На логах DAMP 204 типа из 219 состоят из одного вида строк; детекторы верхних слоёв
  опираются на 2–5 точек. Подход раскрывается на тысячах различных строк.
- **Слова — атомы.** `failed` и `failure` — разные слова. Морфология самих слов (§7.1 в прямом виде)
  не подключена.
- **Строка вне структуры не влияет на код окна.** Уникальная строка без похожих соседей в эмбеддинг окна
  не попадает; инцидент находится по новизне строк, а не по коду окна.
- **Один файл.** Если эталон и цель — один и тот же файл, новых строк нет по определению, а проблемная
  строка считается сигналом, только когда её нет в большинстве эталонных запусков. Для одного длинного
  лога его нужно разрезать на эталонную и целевую части.
- **Предвестники проблем** считаются только для событий, случавшихся не меньше трёх раз.
- **Проблемные слова** (`error`, `failed`, `ошибка`, …) — внешний список; он влияет только на пометки
  в отчёте и на отбор редких проблемных строк в сигналы.
- **Пространство строится заново.** Дообучение на новых строках не реализовано, хотя статья его допускает
  (§7.1.8.2, §8.3.4, §8.3.6).
- **Размер.** Матрица сходства предвычисляется до 8000 точек (`LOG_LAYOUT_MAX_PRECOMPUTE`), то есть
  примерно до 900 различных строк после замены переменных; раскладка большего пространства на CPU
  не проверялась.

```powershell
python log_insights.py                                               # отчёт: log_insights.md, .json и три карты

```

`LOG_INSIGHTS_TARGET`. Образцы логов DAMP — в [log_samples/](../log_samples/).

этот тест пропускается. Папка `data/` в git не входит.
