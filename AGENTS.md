# AGENTS.md — DAMP

Правила работы с репозиторием для агентов (Claude Code и других) и для людей. Файл читается целиком в начале каждой сессии, поэтому здесь только суть. Подробности — в [README.md](README.md), сверка со статьёй — в [docs/ARTICLE_COMPLIANCE.md](docs/ARTICLE_COMPLIANCE.md), версии — в [CHANGELOG.md](CHANGELOG.md).

## Проект в двух словах

DAMP — разреженные битовые коды, их раскладка на двумерной карте и детекторы над картой. Всё делается по статье и её продолжению, проверка — на цифрах MNIST. Проход «код → раскладка → детекторы → эмбеддинг» повторяется по кругу: детали одного уровня становятся стимулами следующего, пока окно не увидит цифру целиком. Версия — `system/damp/__init__.py` (сейчас 0.11.0).

| Этап | Что происходит | Где в коде (`system/damp/`) | Источник |
|---|---|---|---|
| 1. Стимулы | картинка → углопозиции: угол края и клетка сетки 24×24 | `stimuli/` | вне статьи |
| 2. Первичное кодирование ↻ **начало цикла** | угол и место → разреженный код; окно → код «что и где» | `encoding/` | §2, §3.2, §4; П.4–П.7 |
| 3. Раскладка | коды → карта, похожие рядом | `layout/` | §5, §7.1.7 |
| 4. Детекторы и активации | карта → иерархия детекторов; стимул → зажжённые точки → сработавшие детекторы | `activation/` | §6.1–§6.5, §7.1.10–§7.1.11 |
| 5. Эмбеддинги первого уровня | сработавшие детекторы → код детали | `activation/details.py`, `activation/set_embedding.py` | §6.5, §6.6, §7.1.12; П.1 |
| 6. Цикл ↺ **конец цикла** | детали → снова этап 2; окно растёт, пока не увидит цифру целиком | `cycle/` | §6.2, §6.6; П.2, П.3, П.9 |
| 7. Распознавание | детали верхнего уровня голосуют за класс | `decode/` | §2.2.5; мерка вне статьи |

**IMPORTANT:** это видение пайплайна автора проекта. README, рисунки и объяснения строятся ровно по этим семи этапам и их названиям. Если автор меняет схему, первым делом обнови эту таблицу и README.

## Главные правила

1. **Пиши по-русски** — ответы, комментарии, логи, документацию.
2. **Источник истины — статья и её продолжение.**
   - Статья: [docs/DAMP.pdf](docs/DAMP.pdf). Агент читает её текстом: `docs/DAMP_extracted.txt`. В README ссылаться только на PDF.
   - Продолжение: [docs/DAMP_continuation.md](docs/DAMP_continuation.md), разделы П.1–П.9. Весит столько же, сколько статья.
   - Каждое решение сверяй с параграфом. Если отклоняешься, скажи это явно: в коде, в логе и в `docs/ARTICLE_COMPLIANCE.md`.
   - Если в источниках чего-то нет, ищи подсказку в устройстве зрения (V1 → V2 → V4 → IT). Помечай это как доработку и приноси автору готовый план, а не голый выбор.
3. **Порядок работы: план → «делай» → реализация → замер с картинками → отчёт.**
   - Научный план (раздел «Планы») не кодить без прямой команды автора. Перед фазой кодинга план разбирается с автором ещё раз.
   - Пока автор объясняет замысел, ничего не запускай и не меняй: сначала запиши, потом дай план.
   - Короткая фраза автора без «?» может быть вопросом. Согласием считается только прямое «делай».
4. **Опыты — на стенде `bench`**: 5 наборов × 100 обучающих цифр, номера MNIST — случайная выборка с закреплённым зерном (не сплошные блоки: MNIST не перемешан по авторам). **Проверка — на 1 000 отложенных картинок, быстрая проверка — на 100** (`--validation 100`): `select` — выбор настроек, `report` — итог, в выборе не участвует. `test` — один раз в конце этапа. Карта уровня до 5 000 точек. Стенд считает только DAMP: CNN (≈ 86 % без аугментации, ≈ 91 % со сдвигами) и kNN по пикселям (≈ 70 %) — примерный ориентир, сняты один раз, не пересчитывать. Итерации маленькие: одна правка по статье → проверка → короткий отчёт.
5. **Пример — всегда цифра 5, и каждый раз другая** (`LADDER_FIGURE_PICTURE = "random"`): на рисунках и в объяснениях «на одной цифре»; номер её в MNIST показывай.
6. **Ускорять можно только без потери качества.** Результат сверяй цифра в цифру с прежним. На каждый быстрый путь нужен тест, который сравнивает его с прямым.
7. **Версия.** Заметное изменение — новая версия: `system/damp/__init__.py`, запись в `CHANGELOG.md`, строка версии в README.
8. **Git:** коммит и пуш — только по слову автора.
9. **API и журнал всегда актуальны.** Изменил этап, шаг или его данные — в том же изменении обнови:
   - фреймворк `damp_api` и его документацию: кубик этапа, docstring (Google: `Args`, `Returns`, `Raises`, `Example`), README «Фреймворк damp_api» и «Функции API по этапам», ссылки README на код (`python client/apidocs.py --links`), HTML-справку (`python client/run.py docs`);
   - журнал: события этапа (`LOGGER.event`, параграф в конце), вкладку этапа в Rerun и описание путей и шкал в README «Логирование». **Rerun — «живой README»**: вкладки (`system/damp/figures/rerun_cycle.py`) идут в ногу с README — изменился этап, рисунок или число в README, обнови вкладку, её «Что видно» и скриншоты (`python client/run.py figures --rerun`). Вкладка живёт **по ходу счёта**, на одной пятёрке: часть этапа рисуется, как только готова (`LadderObserver.part`), долгий шаг — кадрами (`LOGGER.watch` / `LOGGER.progress`); таблица README «По ходу счёта»;
   - проверь, что запись этапа видна и при повторе из кеша. Стерегут тесты `tests/test_client_api.py`, `ReadmeApiLinksTest` и тест вкладок Rerun.

## Код

Два слоя с корневых папок — так хочет автор:

- **Клиентский** `client/` — всё, чем клиент, оператор и админ управляют нейросетью: `config.toml` (настройки), фреймворк `damp_api/` для программиста, `run.py` (команды поверх фреймворка), `dashboard/` (живой дашборд: сервер и страница), `examples/`. Читается без знания внутренностей.
- **Живой дашборд** (`python client/run.py dashboard`, автор 2026-11-16): главное — рисовать кистью и на одном экране видеть активации всех уровней, кусочки рисунка и как они набиваются в кластеры карт, всё прослеживать; второстепенное убрано. Рисунок идёт через обученный цикл (`damp.cycle.trained` → `TrainedLadder.see`) теми же шагами, что картинка прогона, — цифра в цифру (`tests/test_trained_ladder.py`). Визуализация прогонов по-прежнему в Rerun; дашборд — для того, чего Rerun не может (рисование кистью).
- **Системный** `system/damp/` — под капотом, пакеты по этапам пайплайна.

**IMPORTANT: к системной части — только через клиентскую.** Команды, скрипты, ноутбуки и любой внешний код зовут `damp_api`; в `system/damp` из клиентской части ходит один мост, `client/damp_api/_system.py`. Нужна новая возможность снаружи — добавь метод этапу в `damp_api/stages.py` (и при нужде строку в мост), а не импорт `damp` в UI. Тесты системного слоя проверяют его изнутри. Правило стережёт `tests/test_client_api.py`.

Фреймворк `damp_api` повторяет пайплайн автора: у `Damp()` по полю на этап — `stimuli` (1), `coding` (2, ↻), `layout` (3), `detectors` (4), `embeddings` (5), `cycle` (6, ↺), `recognition` (7), плюс `figures`. Переименовал этап автор — переименуй поле, `STAGES` и таблицу выше.

- **В API — всё, что нужно для своей сборки, а не только готовые прогоны.** У каждого этапа есть кубики (один шаг этапа; результат — часть из `damp_api/parts.py`, идёт в следующий вызов) и готовые прогоны. Пустых этапов нет.
- **Кубики и готовый прогон — одни и те же части системы.** Цикл (`MnistLadderRunner`) повторяет проход `CycleStep` (`system/damp/cycle/step.py`), и кубики API зовут те же его шаги. Тест `CycleBlocksTest`: цикл из кубиков = готовый прогон, цифра в цифру.
- **Свои настройки — через вызовы:** `Damp(changes={...})`, `damp.with_settings(...)`; в системе — `settings.overridden(...)`, выводимые значения пересчитываются. Поэтому значение настройки читается в момент вызова, а не в значении аргумента по умолчанию.
- Части держат системные объекты внутри и отдают простые значения.

Правила:

- **Настройки — только в `client/config.toml`.** Порядок по значимости: сверху то, что сильнее всего меняет результат, внизу техника (скорость, память). Имя ключа совпадает с именем в коде. Код читает настройку как `settings.ИМЯ` в момент вызова (`system/damp/settings.py`); своих чисел в модулях нет. Значения, которые выводятся из других, — правила в `settings.py`, не ключи конфига. Соглашения файла: `"none"` — None, массив — кортеж, `{ smooth = …, article = … }` — значение по режиму раскладки.
- **ООП.** Одно понятие статьи — один класс с понятным именем. В docstring класса и метода — параграф (`§6.5`, `П.5`).
- **Переиспользуй `Layout` и `Encoder`.** Вторую раскладку или второй кодер не пиши. Новые координаты — новые `Dimension` того же `Encoder`; новые карты — тот же `Layout`.
- **Пакеты по этапам:** `stimuli/` (1), `encoding/` (2: всё, что кодирует в разреженные коды), `layout/` (3: всё, что раскладывает по дальнему и ближнему порядку), `activation/` (4–5), `cycle/` (6), `decode/` (7: распознавание, эталоны `baselines.py`, стенд `bench.py`), `figures/` (рисунки, Rerun стенда — `rerun_bench.py`). В корне `damp/` — `settings.py`, `environment.py`, `logging.py`, `article_refs.py`.
- **Только текущий подход.** Прежние опыты удалены и не возвращаются; в истории git они есть.
- **Файлы:** UTF-8; переводы строк сохраняй такими, какие есть в файле (`README.md`, `AGENTS.md` — CRLF).
- **Кеш шагов** (`system/damp/cache.py`): тяжёлый шаг идёт через `CACHE.run(шаг, вход, compute, modules=...)`. Вход — всё, от чего зависит результат, кроме настроек и кода (их ключ берёт сам по `modules`); выход — массивы numpy и простые значения. Шаги независимы: ключ — содержимое входа, а не цепочка предыдущих. Из кеша — то же, что заново, бит в бит: на новый шаг — тест в `tests/test_cache.py`. Дешёвый шаг с огромным выходом не кешировать (так сделано со срабатываниями).

## Логирование

Все события пишутся в одной точке, `system/damp/logging.py`, сразу в консоль, Rerun и файл `logs/damp.jsonl`:

```python
LOGGER.event("ladder.level", section=STIMULUS_DETECTION, data={...})
# консоль: ladder.level level=1 map_points=5000 ... [6.5]
# файл:    {"ts": ..., "run": ..., "level": "info", "event": "ladder.level", "section": "6.5", "data": {...}, "msg": ...}
```

- Логи пишутся **только внутри реализаций**; снаружи — ни `print`, ни логов (кроме итоговых строк команд в `client/run.py`).
- Каждое понятие статьи и каждое преобразование логируется; в конце записи — номер параграфа в `[]`: `[6.5]`, `[П.5]`, иначе `[вне статьи]`. Номера — из `system/damp/article_refs.py`.
- Имя события — `область.объект.действие` латиницей: `layout.phase.long`, `figures.keyhole`. Предупреждения кончаются на `.warning` (в файле `level = "warning"`).
- Файл JSON Lines ротируется по размеру (`LOG_FILE_*`: 20 МБ × 10). Поиск: `rg '"event": "ladder.level"' logs/damp.jsonl`, `jq 'select(.section=="6.5")' logs/damp.jsonl`. `DAMP_LOG_FILE=off` выключает файл (так в тестах).
- Картинки идут в Rerun (`visuals=[LOGGER.visual_image(...)]`), числа — в `data`.

- **README событийно:** любое видимое изменение (команда, структура, замер, этап) — сразу в README, с рисунком. README идёт по семи этапам пайплайна.

5. **§9.3 — сделано (0.10.0):** линейный читатель над нормированными уровнями активации всех уровней (`LinearReader`, `BENCH_LINEAR_DECAYS`) — +5.6 п.п. к «уровни k=3». Итог 0.10.0 на 5 наборах: 70.0 → **81.1 %** (kNN 72.5 %, CNN со сдвигами ≈ 91 %).
6. **Скорость** без потери качества — пока не нужна; **сверка со статьёй** — постоянно (`docs/ARTICLE_COMPLIANCE.md`).
7. **Замер на 1 000 цифр — сделано (0.10.0):** DAMP 91.3 % (2 набора) против kNN 89.5 %; CNN на 1 000 — ориентир ≈ 94–96 %, не мерен. Карта 5 000 точек видит на 1 000 цифрах ~1 % окон — следующий рычаг.

Отложено автором: декодирование «сверху вниз». Проверено и отвергнуто замерами (не предлагать снова без нового довода):

- торможение соседних деталей;
- маска как буквальный XOR;
- объединение всех элементов области (`"max"`);
- окно одного размера на всех уровнях;
- окно первого уровня из трёх штрихов;
- П.7 «в лоб»: окно на 5–7 понятий (33 %), 7 сильнейших понятий большого окна (−26 п.п.), содержание из 5–7 крупных областей (−13 п.п.), код окна короче простым укорочением (−9 п.п.) — пока детали почти все уникальны, урезанное окно теряет цифру;
- ε-окрестность с постоянным ε вместо 1-NN (−9.5 п.п.); класс по господству классов в детекторах (31.7 %);
- код детали только из широких слоёв детекторов (−10 п.п.: коды общие, но не по цифре);
- три масштаба кругов места (§4.5; −4.3 п.п.); окно верхнего уровня на всю цифру — уровень 4 (+1.0 п.п., в пределах шума).
